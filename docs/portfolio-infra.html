문서 성격 본 문서는 인프라 구성에 초점을 맞춘 포트폴리오입니다. 메시지·인증 시퀀스와 설계 방법론은 별권 「백엔드 설계」로 분리했습니다. 계정 ID·리소스 ID·공인 IP·도메인·자격증명 등 식별 가능한 값은 모두 제거하거나 치환했으며, 아키텍처 구조와 설계 의도는 실제와 동일합니다. 모든 구성은 본인이 직접 설계·구축하고 IaC로 코드화한 것입니다.

2. EKS 기반 MSA 표준 구성

버닝갤럭시 · 유니메오 · 엘오디게임즈 — 서비스는 메타버스 · 매칭 플랫폼 · 게임으로 전혀 다르지만, 인프라 구성은 사실상 하나입니다. 세 번에 걸쳐 다듬으며 표준으로 굳어진 구성을 한 번에 정리합니다.

설계 결정 — 왜 같은 구성을 세 번 반복했나 출발점은 다날에서의 경험입니다. 시간이 없어 EKS 구축을 외부 파트너사에 맡겼더니 반복되는 비용과 장애 대응 한계(티켓 대기)가 돌아왔고, Docker·Kubernetes를 학습해 운영을 팀 안으로 가져왔습니다. 이후 세 회사는 서비스 도메인이 전혀 달랐지만 요구 조건 — 무중단 배포 · 서비스 단위 스케일링 · 빠른 롤백 — 은 같았기에, 매번 새 구성을 실험하는 대신 검증된 구성을 재사용하고 다듬는 쪽을 택했습니다. 감수한 것은 Kubernetes 러닝커브와 관리형 서비스의 상시 비용입니다. 러닝커브는 신입이 3개월 안에 VPC 구성부터 CI/CD까지 단독 수행하는 학습 체계로 팀 전체에 상환했고, 그 결과 이 구성은 특정 개인이 아니라 팀이 운영할 수 있는 표준이 되었습니다.

2-1. 전체 아키텍처 — WEB 계층

각 구성 요소의 역할과 트래픽 흐름
  1. ALB (사용자 API) — 사용자 트래픽 진입점HTTPS를 종단하고 Public Subnet에서 Private Subnet의 워커 노드로 트래픽을 넘긴다. Ingress 리소스로부터 자동 생성된다.
  2. ALB (관리자) — 관리자 트래픽 진입점사용자 경로와 로드밸런서를 분리해, 관리자 접근에만 별도의 접근 제한과 인증서 정책을 적용할 수 있게 했다.
  3. ALB Ingress Controller — 로드밸런서 생성·관리 (제어면)트래픽이 지나가는 경로가 아니다. Ingress 리소스를 감시하다가 ALB와 타깃그룹을 만들고 갱신한다. 권한은 IRSA로 위임받아 정적 키를 쓰지 않는다.
  4. auth — 인증 · 인가 전담 서비스JWT를 발급·갱신하고 소셜 로그인과 본인인증을 처리한다. 발급된 토큰은 api·admin이 검증만 하므로 인증 로직이 복제되지 않는다.
  5. api — 사용자 API서비스의 사용자 기능 전반을 담당한다. 요청자는 토큰의 주체로만 식별한다.
  6. admin — 관리자 API동일한 도메인을 전체 데이터 관점에서 조회·관리한다. 역할 기반 권한 체크와 벌크·확장 검색을 추가로 갖는다.
  7. batch — 배치 오케스트레이션워커로 자신을 등록하고 하트비트를 보내며, DB에 저장된 크론 스케줄을 읽어 잡을 실행한다. 정기 집계·정리·외부 연동 잡을 담당한다.
  8. file — 파일 프록시Presigned URL을 발급해 실제 파일 전송은 클라이언트와 S3가 직접 하게 한다. 애플리케이션이 파일 대역폭을 부담하지 않는다.
  9. noti — 실시간 알림 브리지내부 서비스가 REST로 호출하면 Redis에서 사용자↔세션 매핑을 찾아 Socket.IO로 이벤트를 밀어 넣는다.
  10. metrics-server — 리소스 메트릭 수집Pod의 CPU·메모리 사용량을 수집해 HPA가 오토스케일 판단에 쓸 수 있게 한다.
  11. Kubernetes Job — 일회성 DB 작업스키마 마이그레이션·시드·점검을 필요할 때만 실행한다. 상시 접속 가능한 Bastion을 두지 않기 위한 대체 경로다.
  12. RDS MySQL — 업무 DB · 배치 메타 DBPrivate Subnet에 있어 인터넷 경로가 없다. 읽기 트랜잭션은 읽기 전용 커넥션으로 라우팅된다.
  13. ElastiCache Redis — 캐시 · 세션 · 분산 락용도별로 DB 번호를 나눠 인증·블랙리스트·소셜·알림 데이터가 서로 섞이지 않게 했다.

2-2. 네트워크 — 3-Tier VPC

서브넷CIDR가용 IPAZ라우트 테이블 기본 경로
pub-a / pub-c10.1.1.0/24 · 10.1.2.0/24251an-2a / 2c0.0.0.0/0 → IGW

  • 애플리케이션 계층에만 /20 을 할당 — Pod마다 ENI가 붙는 EKS 특성상 IP 소진이 가장 먼저 발생하는 곳이 워커 노드 서브넷입니다. Public·DB는 /24(251개)로 충분하지만 APP은 AZ당 4,091개를 확보했습니다.
  • 환경별 VPC CIDR을 미리 분리 — DEV 10.1.0.0/16 · STG 10.2.0.0/16 · PRD 10.3.0.0/16. 나중에 환경 간 피어링이나 통합이 필요해져도 대역이 겹치지 않도록 설계 시점에 확정했습니다.
  • SG는 참조 체인으로 구성 — sg-cr-pub(사무실 IP ← SSH) → sg-cr-pri-app(SSH ← pub SG) → sg-cr-pri-db-layer(3306·6379 ← VPC 대역). 사람이 들어오는 입구에만 IP를 하드코딩했습니다.
  • EKS 전용 SG 규칙을 별도 정의 — 클러스터 컨트롤플레인 ↔ 노드 간 443 / 1025-65535 통신, ALB → 노드 트래픽을 AWS 권장 규칙에 맞춰 문서화.
  • 네트워크 전체를 CloudFormation 템플릿으로 코드화 — VPC·서브넷·라우트테이블·NAT·SG를 한 스택으로 배포.

  • ECR 태그 정책을 명시적으로 규정 — latest 태그만 쓰면 새 이미지 push 시 기존 이미지가 untagged가 되어, 이미지가 올라간 순간 반드시 배포까지 이어져야 정합성이 유지됩니다. 이 제약을 다이어그램으로 문서화해 팀이 같은 규칙을 지키도록 했습니다.
  • 롤백 시나리오를 사전에 정의 — 배포 실패 시 이전 digest 이미지를 재태깅해 되돌리는 절차를 정리.
  • 환경별 ECR 분리 — DEV 리전과 QA/REAL 리전의 레지스트리를 나누어 승격(promotion) 경로를 명확히 함.

2-4. 파일 서비스와 관측

  • 보안 등급에 따라 다운로드 경로 이원화 — 보안이 필요한 파일은 File 서버를 프록시로 경유하고, 공개 가능한 콘텐츠는 CloudFront에서 직접 서빙. 모든 파일을 프록시로 보내지 않아 서버 대역폭 부담을 줄였습니다.
  • 업로드 카테고리별 버킷 분리 + S3 수명주기 정책 — 접근 빈도가 낮아지는 파일은 Glacier로 자동 전환하거나 자동 삭제해 스토리지 비용을 통제.
  • File 서버 자체를 Scale Out 대상으로 — Auto Scaling Group에 배치해 업로드 트래픽 증가에 대응.

버닝갤럭시 — 0→1 구축과 팀 내재화

EKS 팀 내재화 메타버스 플랫폼을 0→1로 구축하던 시기에 신입 개발자도 평균 3개월 내에 Docker·Kubernetes를 익힌 뒤 AWS에서 VPC 설정부터 CI/CD 구축까지 단독으로 수행할 수 있는 팀 문화를 만들었습니다. 회사 인지도 부족으로 충원이 어려웠기 때문에, 인프라 지식을 특정 개인에게 묶어 두지 않는 것이 곧 프로젝트 리스크 관리였습니다. 전 개발 과정을 문서화해 신규 유입 인원의 온보딩 견해차를 줄였습니다.

유니메오 — 환경 신규 구축

  • 로컬 개발 환경과 AWS 개발 환경을 처음부터 구축 — 신규 시스템이라 개발자가 바로 붙을 수 있는 환경 자체가 없던 상태에서 시작.
  • CloudFormation으로 자원 정의, ECR·CodeBuild로 빌드/배포 파이프라인 구성.
  • 인증 체계 전환 — 소셜 로그인과 자체 SSO(JWT)를 함께 운용하는 구조 설계.
  • 스키마 관리를 Flyway로 코드화 — DB 변경을 배포 파이프라인 안으로 들여와 환경 간 스키마 드리프트를 제거.
이 프로젝트에서 가장 중요했던 일 인프라보다 설계 자체를 되돌린 것이 핵심이었습니다. 5년 전의 잘못된 DB 설계와 정산 개념이 차기 기획서에도 그대로 복제되어 접수 정보 변경·결제 수정·정산 금액 도출이 구조적으로 불가능한 상태였습니다. 약 2개월에 걸쳐 ERD 재작성 → 데이터 관점 flow 설계 → 케이스별 데이터를 직접 전개해 전 부서를 설득하고, 대대적인 설계 변경과 기획 수정을 관철했습니다.

엘오디게임즈 — 게임 도메인 고유 과제

  • 게임 재화의 정합성 — 아이템·번들·재화 구매는 중복 지급이나 이중 차감이 절대 발생하면 안 되는 영역입니다. 외부 락(분산 락)을 도입해 동시 요청에서도 재화 연산이 직렬화되도록 보장했습니다.
  • 실시간 대기큐 — Spring Boot 프로세스 안에서 Socket.IO(Netty) 서버를 함께 구동해 REST와 실시간 채널을 한 배포 단위로 유지. 인프라 구성 요소를 늘리지 않으면서 실시간성을 확보했습니다.
  • 결제 한도 정책 — Google 인앱 결제 연동에 일별 결제 한도를 서버에서 강제.

엘오디게임즈 — 아웃게임 → 인게임 전환 인증

클라이언트는 아웃게임(HTTPS)과 인게임(소켓)을 오가는데, 인게임 서버는 아웃게임의 세션을 알지 못합니다. 그래서 아웃게임 API가 일회용 티켓을 발급해 Redis에 넣고, 인게임 서버가 그 티켓으로 검증하는 구조로 설계했습니다.

3. 메시징 시스템

앞 장의 WEB 계층이 요청에 응답하는 구조라면, 메시징은 요청 없이 먼저 도달해야 하는 구조입니다. 요구되는 성질이 근본적으로 달라서, 같은 클러스터 안에 있어도 별도 계층으로 설계했습니다.

설계 결정 — 저장과 순서와 전달을 분리 메신저는 쓰기가 몰리고 읽기는 기기마다 제각각인 워크로드입니다. 그래서 메시지 본문은 쓰기에 강한 Cassandra에 적재하고, 순서 보장(시퀀스)과 읽음 위치(Read Index)는 Redis가, 실시간 전달은 MQTT(AmazonMQ) 브로드캐스트가 맡도록 역할을 셋으로 나눴습니다. RDB 하나로 시작하면 개발은 단순하지만 수평 확장 시 가장 먼저 무너지는 지점이 메시지 테이블이라는 것을 알고 있었기에, 처음부터 저장·순서·전달을 분리했습니다. 대가로 세 저장소의 정합성을 애플리케이션이 책임져야 하며, 그 규칙(어디가 진실의 원천인지)을 아래 도식들이 기록합니다.

3-1. 메시징 서비스 구성

각 서비스의 역할과 데이터 흐름
  1. Msg Proxy — 메시지 송수신 API 서버유저가 보낸 메시지를 받아 ① 바로 받지 못하는 대상을 위해 Cassandra에 저장하고 ② MQ로 전송하며(OpenWire 프로토콜) ③ 특정 시점 이후의 메시지를 조회해 주고 ④ 모바일 push를 위해 알람 큐에 적재한다.
  2. Auth — 인증 · 인가 서버로그인·로그아웃·탈퇴 등 계정 관련 API를 처리한다. 유저의 친구나 기존 로그인 기기에 이벤트를 실시간으로 전달해야 할 때는 notice 큐에 적재한다.
  3. Admin — 운영 관리 시스템관리자가 회원에게 직접 메시지를 보내거나 계정 차단을 변경한다. 관리자 액션 중 실시간 대응이 필요한 건은 noti 큐로 넘긴다.
  4. Noti — 실시간 시스템 메시지 전달MQ를 통해 접속 중인 클라이언트에게 시스템 메시지를 실시간으로 전송한다.
  5. Alarm — 모바일 푸시 발송Amazon SNS를 거쳐 FCM / APNS로 push message를 전달한다. 상대 기기에 메시지가 도착했음을 알리는 역할.
  6. File — 파일 프록시파일 업로드를 담당한다. 보안성이 높은 파일은 S3에서 직접 내려주지 않고 File 서버를 경유해 다운로드시킨다.
  7. Rest API — 비즈니스 로직유저 계정 인덱스로 DM 목록 전체를, 또는 상대 계정 인덱스로 특정 상대와의 DM만 조회한다. 호출된 로직에 따라 RDB에 저장하고, notification 큐로 대상 유저에게 가져갈 메시지·이벤트가 있음을 알린다.

3-2. MQ 가용성 — 프로토콜 계층별 분리

3-3. 알림 경로 3종 — 수신자 상태에 따른 분기

각 경로의 역할과 선택 기준
  1. 경로 A — MQ topic — 방 단위 브로드캐스트채팅방처럼 다수가 같은 이벤트를 동시에 받아야 할 때 쓴다. 구독 모델이라 수신자가 늘어도 발신 측 비용이 늘지 않는다. 단, 그 순간 접속해 있는 사람에게만 도달한다.
  2. 경로 B — Socket.IO 세션 — 특정 사용자 지목 전송"이 사용자에게만" 보내야 할 때 쓴다. Redis에 저장된 userId ↔ 세션 매핑으로 대상 소켓을 찾는다. 방 개념이 없는 알림(친구 요청, 상태 변경)에 적합하다.
  3. 경로 C — SNS → FCM / APNS — 미접속 사용자앱이 꺼져 있으면 A·B 어느 쪽도 도달하지 못한다. 이때만 모바일 푸시를 태운다. 외부 공급자를 거치므로 전달 지연과 실패를 전제하고, 도착 보장은 조회 경로가 대신한다.

3-4. 실시간 채널 — 대기큐와 타이머

메시지 전달 외에도 연결을 유지한 채 서버가 상태를 밀어 넣어야 하는 요구가 반복적으로 나왔습니다.

  • 게임 대기큐 — Spring 프로세스 안에서 Socket.IO(Netty) 서버를 함께 구동했습니다. REST와 실시간 채널이 한 배포 단위라 인프라 구성 요소를 늘리지 않으면서 실시간성을 확보했습니다. 대기 순번은 Redis에 두어 서버가 재기동돼도 순서가 유지됩니다.
  • Redis ZSET 기반 타이머 — 만료 시각을 score로 저장하고 짧은 주기로 폴링합니다. 만료 항목이 나오면 애플리케이션 이벤트로 발행해 비동기로 처리하고, 필요하면 다시 스케줄합니다. 스케줄러를 따로 두지 않아도 "N초 뒤에 이 사용자에게 알림" 같은 요구를 처리할 수 있습니다.
  • 다중 인스턴스 중복 실행 방지 — 폴링은 모든 인스턴스가 동시에 수행하므로 분산 락으로 한 번만 실행되도록 직렬화했습니다.
  • 수평 확장의 한계를 명시했다 — 세션 매핑을 로컬 메모리에서 찾는 구조는 인스턴스가 늘면 다른 인스턴스의 세션을 찾지 못합니다. Redis Pub/Sub 브리지나 스토어 팩토리로 해결해야 한다는 점을 문서에 남겨, 확장 시점에 다시 설계하지 않아도 되게 했습니다.

4-2. DEV — 단일 EC2 통합 구성

한 인스턴스 안에서의 요청 흐름
  1. nginx — 경로 기반 리버스 프록시ALB가 넘긴 요청을 경로 prefix로 판별해 컨테이너로 분배한다. 서비스가 늘어도 ALB 규칙을 건드리지 않고 nginx 설정만 고치면 된다.
  2. auth — 인증 · 인가로그인과 토큰 발급을 담당한다. 나머지 서비스는 발급된 토큰을 검증만 한다.
  3. api — 사용자 API학습·콘텐츠·상점 등 사용자 기능 전반.
  4. admin — 관리자 API같은 데이터를 운영자 관점에서 조회·수정한다.
  5. batch — 배치 스케줄러크론 스케줄에 따라 집계·정리 잡을 실행하고 실행 이력을 기록한다.
  6. file — 파일 프록시업로드/다운로드 경로를 중계하고 Presigned URL을 발급한다.
  7. noti — 실시간 알림REST 요청을 받아 접속 중인 클라이언트에게 Socket.IO로 이벤트를 전달한다.
  8. MySQL — 업무 DB · 배치 메타 DB별도 인스턴스가 아니라 같은 호스트의 컨테이너다. 네트워크 홉이 없어 빠르지만 백업·복구는 보장되지 않으므로 개발 데이터에 한정한다.
  9. Redis — 세션 · 캐시 · 분산 락 · 타이머인증 상태와 캐시뿐 아니라 알림 서비스의 타이머 큐, 재화 정합성이 필요한 연산의 분산 락도 여기서 처리한다.

API 서버 6종과 MySQL·Redis를 한 대의 EC2 안에서 docker-compose로 함께 구동하는 구성입니다. 개발 단계에서 가장 빠르게 반복하기 위한 의도적인 단순화이며, 데이터 계층 분리는 STG 이후로 미뤘습니다.

4-3. STG(미국) — 데이터 계층 분리

각 구성 요소의 역할과 접근 통제
  1. ALB — 외부 진입점인터넷 전체에 80/443만 열려 있는 유일한 지점. 여기서 HTTPS를 종단한다.
  2. EC2 (docker-compose) — 애플리케이션 6종ALB의 Security Group에서 오는 트래픽만 받는다. IP가 아니라 SG를 참조하므로 인스턴스를 교체해도 규칙을 고칠 필요가 없다.
  3. RDS MySQL 8.4 — 업무 DB3306은 애플리케이션 SG에서만 접근할 수 있다. 스토리지는 암호화되어 있고 마스터 비밀번호는 코드·설정 어디에도 없다.
  4. ElastiCache Redis — 캐시 · 세션6379를 애플리케이션 SG에만 개방한다.
  5. Secrets Manager — DB 자격 관리RDS 마스터 비밀번호를 자동 생성·교체한다. 애플리케이션은 최소 권한 계정만 사용한다.
  6. CloudFront — 콘텐츠 전송OAC로 S3에 접근하고 Viewer Function이 경로 prefix를 변환한다.
  7. S3 (서울 리전) — 콘텐츠 버킷미국 리전에서도 서울 버킷을 그대로 오리진으로 쓴다. 버킷 이중 구축과 동기화 파이프라인을 만들지 않기 위한 선택.

실제 서비스 리전인 미국(us-west-1)에 STG를 재구축하면서, 서울 STG를 해제하고 데이터 계층을 관리형 서비스로 분리했습니다. 동시에 NAT Gateway를 제거해 고정비를 낮췄습니다.

주요 설계 결정

  • Security Group은 CIDR이 아니라 SG 참조로 연결 — ALB SG → App SG → RDS/Redis SG 체인. CIDR 하드코딩은 SSH·직접 DB 접속용 사무실 IP 하나뿐이어서, 인스턴스가 바뀌어도 규칙을 고칠 일이 없습니다.
  • NAT Gateway 제거 — 모든 자원을 Public 서브넷에 두고 IGW로 직접 아웃바운드. Private 계층을 없앤 대신 SG를 촘촘히 설계해 통제. 월 약 $32 절감이며, PROD에서는 다시 3-Tier + NAT로 복원합니다.
  • RDS 마스터 비밀번호는 Secrets Manager 자동 관리 — 코드·설정 어디에도 평문 비밀번호가 없고, 애플리케이션은 별도 최소 권한 계정만 사용합니다.
  • 스토리지 암호화 활성화 — RDS gp3 스토리지 암호화 적용(DEV의 미암호화 EBS를 STG에서 교정).
  • ARM 인스턴스(t4g) 채택 — 동급 x86 대비 비용 효율이 높아 DB 계층에 우선 적용.
  • 파라미터 그룹으로 문자셋·타임존 고정 — utf8mb4 / utf8mb4_0900_ai_ci를 서버 레벨에서 강제해 환경별 정렬·인코딩 차이를 원천 차단.
  • DB 초기화는 1회성 스크립트로 코드화 — 데이터베이스·계정·권한 생성까지 스크립트에 포함, 스키마 자체는 애플리케이션의 Flyway가 담당하도록 역할을 분리.

4-4. PROD — 2장의 표준 구성으로 이행

운영 환경은 2장에서 정리한 EKS 표준 구성을 그대로 적용할 예정이며, IaC로 완성해 검증까지 마친 상태입니다. 비용 때문에 상시 가동하지 않을 뿐, 약 20분 만에 재생성할 수 있습니다. 다만 세 회사에서 쓰던 구성을 그대로 두지 않고 아래 네 가지를 바꿨습니다.

  • Bastion을 두지 않음 — 상시 노출되는 서버 자체를 없애고, EKS API는 Public Endpoint + CIDR 제한 또는 CloudShell로 접근. 관리 대상과 공격 표면을 동시에 줄이는 선택입니다.

4-5. CDN — 단일 CloudFront로 10개 버킷 라우팅

콘텐츠 종류별로 S3 버킷을 나누되, CloudFront 배포는 하나만 두었습니다. 배포·인증서·도메인을 늘리지 않으면서 버킷을 분리하기 위한 구성입니다.

  • 버킷별 Cache Behavior + OAC — 강의 · 챕터 · 문항 · 퀴즈 · 프로필 · 대학 · 코스 · 학습 · 모듈 · 리소스 등 콘텐츠 도메인별로 버킷을 분리하고, 각 버킷은 Origin Access Control로 CloudFront에서만 접근 가능하게 잠금. 버킷 자체는 Block Public Access 상태입니다.
  • CloudFront Function으로 경로 변환 — 클라이언트는 /{종류}/{파일}로 요청하지만, S3에는 종류 prefix 없이 저장됩니다. viewer-request 함수가 prefix를 제거해 버킷 내부 구조와 외부 URL 규칙을 분리했습니다.
  • 업로드는 Presigned URL — 파일 서비스가 URL만 발급하고 실제 트래픽은 S3로 직접 흐르게 해, 애플리케이션 서버가 파일 대역폭을 부담하지 않습니다. 대량 등록은 엑셀 기반 벌크 발급으로 처리.
  • 리전 간 재사용 — 미국 STG에서도 서울의 콘텐츠 버킷을 그대로 오리진으로 사용해 버킷 이중 구축과 동기화 파이프라인을 만들지 않았습니다.

4-7. 비용 설계

런칭 전 단계에서 인프라 고정비는 그 자체로 리스크입니다. "필요할 때만 켜고, 꺼도 복구가 보장되는" 구조를 만들어 유휴 비용을 최소화했습니다.

상태월 비용(추정)구성

  • 클러스터 해제 시 월 $200대 → $32 — 네트워크·IAM 정책·ECR만 남기고 컴퓨팅을 내리는 방식. 재구축이 20분이므로 "필요할 때만" 켜는 운영이 실제로 가능합니다.
  • 미국 STG에서 NAT 제거로 월 ~$32 절감 — Public-only VPC + SG 통제로 대체. DB 계층은 ARM(t4g) 인스턴스를 채택했습니다.

5. 인프라 설계 원칙

네 곳의 환경을 거치며 일관되게 지켜 온 기준입니다.

원칙구체적 실천적용 사례
단계에 맞는 복잡도 런칭 전에는 단일 서버로 단순하게, 확장이 필요해지는 시점에 전환. 단 전환 대상은 미리 코드로 완성해 둔다 Chalk — 단일 EC2로 개발하면서 EKS는 IaC로 완성·검증 후 해제 보관
이름이 곧 구조도 {env}-{region}-{resource}-{system}-{purpose}-{az} 규칙을 모든 자원에 적용 Chalk 전 환경 / 버닝갤럭시 VPC·서브넷·SG
CIDR이 아니라 SG 참조 ALB SG → App SG → DB SG 체인으로 연결. CIDR 하드코딩은 사람이 접근하는 경로에만 Chalk 미국 STG — 인스턴스 교체 시 규칙 수정 불필요
상시 노출 경로를 만들지 않는다 Bastion 제거, DB 직접 접속 대신 Job/CloudShell, 외부 노출은 로드밸런서 한 경로로 통일 Chalk EKS — Bastion 없이 Kubernetes Job으로 DB 작업
권한은 키가 아니라 역할로 워크로드 인증에 IRSA 사용, 정적 Access Key를 클러스터에 두지 않음. 비밀번호는 Secrets Manager Chalk EKS(IRSA) / 미국 STG(Secrets Manager)
내릴 수 있어야 올린 것이다 모든 스택에 생성과 역순 해제 스크립트를 쌍으로 작성. 파괴적 작업은 이중 확인, 데이터 자원은 Retain Chalk — cluster-up/down, stack-up/down
비용은 설계 변수다 가용성이 필요 없는 환경에서는 NAT·Multi-AZ·관리형 서비스를 의도적으로 빼고, 그 트레이드오프를 문서에 남긴다 Chalk — 유휴 시 월 $32 / NAT 제거로 $32 절감
프로토콜에 맞는 계층 선택 HTTP는 L7(ALB), 비 HTTP는 L4(NLB). 무리하게 하나로 통일하지 않는다 버닝갤럭시 — MQ는 NLB, 웹 콘솔은 ALB
결정은 문서로 남긴다 변경 불가능한 제약(immutable 이름), 의도적으로 감수한 리스크, 환경 간 차이를 표로 정리해 보고서로 축적 Chalk — 자원 감사·네이밍 정리·타임존 전략 등 20여 건의 결정 기록
