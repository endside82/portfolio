1. 메시지 송수신 설계

메타버스 플랫폼과 모바일 메신저에서 사용한 메시지 파이프라인. 핵심은 하나의 저장소에 모든 걸 맡기지 않는 것이었습니다.

1-1. 왜 메시지 프록시를 두었나

클라이언트가 메시지 큐에 직접 붙거나 P2P로 주고받는 구조도 가능합니다. 그렇게 하지 않은 이유는 세 가지입니다.

  • 인증을 큐에 맡길 수 없다 — 브로커의 인증 모델은 서비스의 권한 정책(차단·탈퇴·강제 로그아웃)을 표현하기에 부족합니다. 프록시를 두면 메시지 한 건마다 서비스 규칙으로 걸러낼 수 있습니다.
  • 과거 메시지를 큐가 책임지지 않는다 — 큐는 "지금 연결된 사람에게 전달"이 본업입니다. 접속하지 않았던 구간의 메시지는 별도 저장소에서 다시 읽어와야 하고, 그 조회 창구가 필요합니다.
  • 클라이언트를 단순하게 유지해야 한다 — 시퀀스 발급·저장·알림·조회가 각각 다른 저장소를 쓰는데, 이걸 클라이언트가 알게 하면 스펙 변경 때마다 앱을 다시 배포해야 합니다.

1-2. 송수신 시퀀스 — 저장소를 역할별로 나누기

저장소담당선택 이유
Cassandra메시지 본문메시지는 수정되지 않고 계속 쌓이기만 하는 데이터입니다. 쓰기가 대부분이고 방 단위 범위 조회만 필요하므로, 쓰기에 유리하고 수평 확장이 쉬운 쪽을 골랐습니다.
Redis방 시퀀스 · 사용자별 읽음 위치메시지마다 원자적으로 증가하는 번호가 필요합니다. RDB의 시퀀스나 auto-increment는 방마다 만들 수 없고 경합도 큽니다.
MQ실시간 전달구독 모델이 필요한 건 "지금 접속 중인 사람"뿐입니다. 전달 실패는 조회 경로가 보완하므로 브로커에 영속성을 요구하지 않았습니다.
RDB방 · 참여자 정보관계와 권한이 필요한 메타데이터만 남겼습니다.

1-3. 읽음 처리 — 안 읽은 개수를 조회 없이 구하기

메신저에서 가장 자주 호출되는 값이 "안 읽은 메시지 수"입니다. 방 목록을 열 때마다 모든 방에 대해 계산되기 때문에, 이걸 메시지 테이블 조회로 구하면 방이 늘어날수록 비용이 선형으로 커집니다.

안 읽은 수 = 방의 최신 msg_idx − 내 read_idx
두 값 모두 Redis에 있는 정수라서, 방이 몇 개든 조회 없이 뺄셈 한 번으로 끝납니다.
  • 단체방의 "n명 읽음"도 같은 원리 — 참여자별 read_idx를 모아 특정 msg_idx보다 큰 값의 개수를 세면 됩니다. 메시지마다 읽음 레코드를 남기지 않아도 됩니다.
  • 클라이언트 로컬 DB와의 정합 — 앱은 마지막으로 받은 msg_idx만 기억하면 되고, 재접속 시 그 지점부터 요청합니다. 서버는 "누가 무엇을 받았는지" 추적할 필요가 없습니다.
  • 순서 보장의 근거를 한 곳에 모았다 — 메시지 순서는 오직 방 시퀀스가 결정합니다. 클라이언트 시각이나 서버 수신 시각에 의존하지 않기 때문에, 서버가 여러 대여도 순서가 흔들리지 않습니다.

2. 인증 설계

여러 회사에서 반복적으로 다시 만든 영역입니다. 매번 같은 질문이 나왔습니다 — 토큰을 얼마나 오래 살릴 것인가, 누가 검증할 것인가, 그리고 이 사람이 정말 본인인가.

2-1. JWT 발급 · 검증 · 갱신

  • OS별로 토큰을 분리 발급 — 같은 계정이라도 기기 종류별로 토큰을 나눠, 한쪽에서 로그아웃해도 다른 기기의 세션이 끊기지 않게 했습니다. 반대로 "다른 기기에서 로그인함" 정책이 필요할 때도 대상 토큰만 무효화하면 됩니다.
  • JWT는 서버가 회수할 수 없다 — 그래서 로그아웃·탈퇴·강제 차단은 Redis 블랙리스트로 처리하고, 등록 기간은 토큰의 남은 만료시간만큼만 둡니다. 만료된 뒤에는 어차피 검증에서 걸리므로 저장소가 무한정 커지지 않습니다.
  • 에러 코드를 도메인별로 대역 분리 — JWT/인증 · 가입 · 로그인 · 소셜 · 본인인증을 각각 다른 번호 대역에 배치했습니다. 클라이언트가 코드 앞자리만 보고 분기할 수 있어, 새 에러가 늘어도 앱 수정이 필요 없습니다.
  • 인증 서버를 별도 서비스로 분리 — 발급은 Auth 한 곳에서만 하고, 사용자 API와 관리자 API는 검증만 합니다. 인증 로직이 여러 서비스에 복제되지 않습니다.

2-2. JWKs(RSA) — 비밀키를 공유하지 않는 검증

  • 검증자가 비밀키를 갖지 않는다 — 서비스가 6개든 10개든 개인키는 Auth 한 곳에만 있습니다. 다른 서비스가 침해돼도 토큰을 위조할 수 없습니다.
  • 키 교체가 무중단으로 가능 — JWKS는 여러 키를 동시에 게시할 수 있어, 새 키로 발급을 시작하면서 기존 키로 서명된 토큰도 만료될 때까지 계속 검증됩니다. 대칭키였다면 전 서비스를 동시에 재배포해야 합니다.
  • 공개키는 캐시한다 — 매 요청마다 JWKS를 가져오면 Auth가 병목이 되므로, 검증자는 키를 캐시하고 키 ID가 바뀔 때만 다시 조회합니다.

2-3. Refresh Token 주기 정책

토큰 수명은 보안과 사용성이 정면으로 충돌하는 지점입니다. 짧게 잡으면 자꾸 로그인을 요구하고, 길게 잡으면 탈취됐을 때 오래 살아남습니다.

  • Refresh 만료 시점에 재로그인을 강요하지 않는다 — 갱신 응답에 새 Refresh를 함께 담아, 활성 사용자는 끊김 없이 이어집니다.
  • 대신 미사용 계정은 확실히 만료시킨다 — 갱신이 일어나지 않으면 Refresh도 갱신되지 않으므로, 방치된 세션은 30일 뒤 자동으로 끊깁니다.
  • 재발급 구간을 명시적으로 정의했다 — "만료 며칠 전부터 새 Refresh를 내려줄지"를 정책 값으로 두어, 운영 중에 정책만 바꿀 수 있게 했습니다.

2-4. 소셜 로그인 + 본인인증(CI) 가입

소셜 로그인은 "이 사람이 그 소셜 계정의 주인"임을 증명할 뿐, 실명을 보증하지는 않습니다. 실명 확인이 필요한 서비스에서는 소셜 인증과 본인인증을 같은 사람의 행위로 묶는 절차가 별도로 필요합니다.

  • 본인인증은 앱이 제공자와 직접 진행한다 — 인증 화면은 제공자가 소유하므로 서버가 중간에 낄 수 없습니다. 서버는 트랜잭션 ID만 들고 있다가 끝난 뒤 결과를 조회합니다.
  • 그 사이에 사람이 바뀔 수 있다 — 소셜 인증과 가입 요청 사이에 시간이 벌어지기 때문에, 서버는 소셜 자격증명을 보관하고 유효코드를 발행해 같은 세션의 연속임을 확인합니다.
  • CI를 중복 가입 판별 기준으로 삼는다 — 소셜 계정은 얼마든지 새로 만들 수 있지만 CI는 사람당 하나입니다. 탈퇴 후 재가입 정책·중복 계정 제한이 모두 이 값 위에서 성립합니다.
  • 제공자별 차이는 Verifier로 흡수 — Google·Kakao·Naver는 토큰 검증 방식이 제각각입니다. 제공자마다 Verifier 구현을 두고 상위 흐름은 동일하게 유지해, 제공자 추가가 코드 한 개 추가로 끝나게 했습니다.

2-5. OTP 기반 이메일 · SMS 인증

  • 발송 횟수를 Redis에 함께 저장 — 같은 주소로 무제한 발송을 요청하는 것을 막습니다. TTL이 붙어 있어 별도의 정리 작업이 필요 없습니다.
  • 같은 구조를 용도별로 재사용 — 가입 · 비밀번호 재설정 · 이메일 변경 · 소셜 계정 연결에 동일한 OTP 파이프라인을 쓰되, 용도를 키에 포함시켜 서로 섞이지 않게 했습니다.
  • 로컬 개발에서는 발송을 우회 — 개발 프로파일에서는 메일을 실제로 보내지 않고 형식만 검증합니다. 다만 비밀번호 재설정처럼 보안이 중요한 용도는 우회 대상에서 제외했습니다.

2-6. UGC 인증 — 외부 앱에 신원을 위임하는 법

외주 개발사나 서드파티가 만든 앱이 우리 사용자 정보를 필요로 할 때, 우리 계정 토큰을 그대로 넘기는 것은 위험합니다. 넘긴 순간 통제권이 사라지기 때문입니다.

2-7. 앱 버전 강제 업데이트

모바일 앱은 사용자가 업데이트하지 않으면 구버전이 계속 서버를 호출합니다. API 스펙이 바뀌었는데 구버전이 붙으면 데이터가 깨지므로, 버전을 서버가 강제할 수 있어야 합니다.

  • 버전 정보를 토큰에 담았다 — 앱이 헤더로 보내는 버전 값은 클라이언트가 조작할 수 있습니다. 발급 시점의 버전을 토큰 클레임에 넣으면 서명으로 보호되므로 위조할 수 없습니다.
  • 강제 업데이트는 전용 응답 코드로 — 서버가 정해진 코드를 내려보내면 앱은 업무 화면 대신 업데이트 안내로 전환합니다. 업무 로직을 타기 전에 걸러냅니다.
  • 업데이트 후에는 토큰을 갱신해야 한다 — 앱 버전이 올라가도 토큰 안의 버전은 옛날 값이므로, 업데이트 직후 갱신을 한 번 태워 두 값을 맞춥니다. 이 단계를 빠뜨리면 업데이트를 했는데도 계속 안내 화면이 뜹니다.

3. 파일 보안 설계

파일은 전부 보호하면 비싸고, 전부 열면 위험한 자원입니다. 그래서 보호 수준을 하나로 정하지 않고 콘텐츠 성격에 따라 경로를 나눴습니다.

각 구성 요소의 역할과 파일 흐름
  1. CloudFront — 공개 콘텐츠 전송강의 영상·썸네일처럼 노출돼도 무방한 파일을 CDN 캐시에서 바로 내려준다. 애플리케이션 서버를 거치지 않으므로 트래픽이 늘어도 서버 부하가 증가하지 않는다.
  2. S3 (OAC) — 공개 콘텐츠 저장소버킷 자체는 Block Public Access 상태다. CloudFront의 OAC를 통해서만 읽을 수 있어, 버킷 주소가 알려져도 직접 받아갈 수 없다.
  3. File 서버 (프록시) — 보안 파일 중계요청자의 권한을 확인한 뒤 S3에서 읽어 스트리밍한다. 클라이언트는 S3 주소를 알지 못하며, 권한이 회수되면 즉시 차단된다.
  4. S3 — 보안 파일 저장소File 서버만 접근할 수 있다. 업로드는 Presigned URL로 클라이언트가 직접 올리되, 다운로드는 반드시 프록시를 거친다.
  5. Glacier — 장기 보관접근 빈도가 떨어진 파일을 수명주기 정책에 따라 자동 전환한다. 삭제 대신 저비용 계층으로 옮겨 보관 의무와 비용을 함께 만족시킨다.
  • Presigned URL로 트래픽을 서버에서 걷어냈다 — 파일 서비스는 서명된 URL만 발급하고 실제 전송은 클라이언트와 S3가 직접 합니다. 애플리케이션 서버가 파일 크기만큼의 대역폭을 부담하지 않습니다.
  • 대량 등록은 엑셀 기반 벌크 발급 — 운영자가 콘텐츠 수백 건을 올릴 때 URL을 한 번에 발급하고, 결과도 엑셀로 되돌려 어떤 행이 실패했는지 그대로 확인하게 했습니다.
  • 버킷을 콘텐츠 종류별로 분리 — 종류마다 수명주기·접근 정책이 다르기 때문입니다. 접근 빈도가 낮아지는 파일은 저비용 스토리지로 자동 전환하거나 만료시킵니다.
  • 버킷 자체는 열지 않는다 — 공개 콘텐츠라도 S3는 Block Public Access 상태로 두고 CDN(OAC)에서만 접근하게 했습니다. 버킷 주소가 유출돼도 직접 받아갈 수 없습니다.

4. 설계 방법론

기술적으로 옳은 설계라도 관련 부서가 이해하지 못하면 채택되지 않고, 이해했더라도 구현이 끝난 뒤에 발견된 오류는 되돌릴 수 없습니다. 이 두 문제를 다루기 위해 쓰는 방법이 있습니다.

4-1. 도식화 — 비개발자를 설득하는 언어

DB 설계를 설명할 때 ERD만 내밀면 초보 개발자·비서버 개발자·상급자는 데이터의 흐름을 읽어내지 못합니다. 테이블 관계는 "무엇이 있는가"를 말할 뿐, "언제 무엇이 생기고 무엇이 사라지는가"를 말해주지 않기 때문입니다. 그래서 설계를 바꿔야 할 때는 아래처럼 상태와 전이로 다시 그립니다.

  • 정상 흐름과 취소 흐름을 같은 그림에 둔다 — 대부분의 설계 사고는 "취소하면 어떻게 되는가"에서 발생합니다. 정상 경로만 그리면 이 질문이 회의에서 나오지 않고, 구현 단계에서 뒤늦게 터집니다.
  • 생성 순서와 삭제 순서를 명시한다 — 스케줄·금액·결제·정산은 만들어진 순서의 역순으로만 안전하게 되돌릴 수 있습니다. 이 규칙을 그림에 박아두면 이후 기능이 추가돼도 같은 원칙이 적용됩니다.
  • 시간이 트리거인 전이를 빠뜨리지 않는다 — "보증금 미납 상태로 일정 시간 경과 시 자동 취소" 같은 전이는 사용자 행동이 없어 놓치기 쉽습니다.
  • 시간은 더 들지만 회의 시간이 줄어든다 — 그리는 데 하루가 더 걸려도, 오해로 인한 재작업과 반복 설명이 사라져 전체로는 빨라집니다. 실제로 이 방식으로 5년간 잘못 복제돼 온 정산 설계를 바로잡고 기획서까지 수정한 적이 있습니다.

4-2. 데이터 나열 — 구현 전에 설계를 검증하기

설계가 끝나고 나면 보통 바로 구현에 들어갑니다. 그런데 구현이 완료된 뒤에 발견된 설계 오류는 수정 비용이 극단적으로 큽니다. 그래서 복잡한 도메인에서는 구현 전에 예상 데이터를 직접 나열해 보는 단계를 넣습니다.

  • 정상 케이스만으로는 부족하다 — 예외 케이스까지 데이터를 늘어놓아야 구현 오류나 설계에서 놓친 부분이 드러납니다. 머릿속으로만 하면 반드시 편한 케이스만 검토하게 됩니다.
  • 하루이틀이면 끝나는 작업이다 — 반면 구현이 완성된 뒤의 설계 수정은 며칠에서 몇 주가 듭니다. 비용 비교가 명확해서 복잡한 상황일수록 이 방법을 선택합니다.
  • 그대로 테스트 케이스가 된다 — 나열한 데이터가 곧 기대값이므로, 검증에 쓴 표를 그대로 테스트 픽스처로 옮길 수 있습니다.
  • 논쟁을 줄인다 — 팀원이나 타 부서와 의견이 갈릴 때, 데이터가 눈앞에 있으면 "이해한 척 넘어갔다가 구현 후 전혀 다른 결과가 나오는" 상황을 막을 수 있습니다.

4-3. 문서 기반 AI 개발 프로세스

AI 코딩 에이전트(Claude Code)를 실무에 넣었을 때 가장 큰 문제는 속도가 아니라 "했다고 보고하지만 안 한 작업"이었습니다. 지적한 것만 고치고 같은 패턴의 나머지는 그대로 두는 식입니다. 그래서 규칙을 문서로 고정하고, 증거 없는 보고를 반려하는 절차를 만들었습니다.

이 프로세스가 막으려 한 것
  1. 부분 점검 — 일부만 확인하고 "문제 없음"으로 보고해결: 전수 조사 강제. 심볼 검색으로 모든 인스턴스를 찾고 전체 목록을 먼저 만들게 했습니다.
  2. 증상 치료 — 지적받은 항목만 고치고 같은 패턴의 나머지는 방치해결: 참조 구현과의 비교표를 강제. 표를 채우려면 전체를 봐야 하므로 부분 수정이 성립하지 않습니다.
  3. 증거 없는 보고 — "대부분 괜찮습니다" 같은 검증 불가능한 결론해결: 파일 경로 + 라인 번호 + 문제 개수를 필수 출력 형식으로 규정. 없으면 반려합니다.
  4. 미완결 — 코드만 고치고 빌드는 확인하지 않음해결: 빌드 검증까지를 완료 조건에 포함시켰습니다.

  • 공용 지식 저장소를 별도로 뒀다 — 프로젝트별 규칙과 별개로, 기술 스택 · 템플릿 · 서비스 간 API 레퍼런스 · 워크플로를 한곳에 모아 저장소를 넘나드는 작업에서도 같은 기준이 적용되게 했습니다.
  • 코드 심볼 검색 도구를 연동 — 텍스트 grep이 아니라 심볼 단위로 참조를 찾게 해, "전수 조사"가 실제로 전수가 되도록 보장했습니다.
  • 결론 — AI를 쓰느냐 마느냐가 아니라, AI가 만든 결과를 무엇으로 검증하느냐가 실제 생산성을 갈랐습니다. 검증 규칙이 없을 때는 리뷰 비용이 작성 비용을 넘어섰습니다.
